# Invoices–Portal Integration Analysis

## 1. How Customers View/Pay for Invoices via the Portal

### Access mechanism
- Customers access the portal via an **order token** (`orders.orderToken`), not via auth. The token is a 32-char hex string generated by `generateOrderToken` (`src/features/portal/model.ts:64-70`).
- The `PortalPage` component (`src/features/portal/pages/portal-page.tsx`) routes to one of four views based on order status: `draft`, `pending`, `rejected`, or **progress** (approved/production/in_delivery/completed).

### Invoice display
- Invoices are embedded in the order payload fetched by `getPortalOrder` (`src/features/portal/model.ts:72-200`). The query JOINs `invoices` with `payment_methods` and checks for payment-proof assets.
- `PortalInvoice` type (`src/features/portal/model.ts:35-48`) exposes:
  - `invoiceNumber`, `total`, `percentage`, `dueDate`, `status`
  - Payment method details (name, bank, account number, account holder, instructions)
  - `hasPaymentProof` boolean — true if an asset with `usage='payment_proof'` exists for that invoice

### Rendering
- **`PaymentAlertBanner`** (`src/features/portal/components/payment-alert-banner.tsx`): A top-level alert shown when unpaid invoices exist. Shows total unpaid count + amount, flags overdue (destructive variant) or due-soon states.
- **`PaymentSection`** (`src/features/portal/components/payment-section.tsx`): Renders each invoice as a card with:
  - Invoice number, percentage, amount (IDR currency)
  - Due date
  - Payment method bank details (if attached)
  - Status badge (with overdue/pending-confirmation variants)
  - **Upload proof button** (for unpaid invoices)
  - **Download invoice PDF link** → `/api/documents/invoices/token/${inv.id}`

### Payment proof upload flow
1. Customer selects a file (image or PDF) → `handleUpload` in `ProgressView` (`src/features/portal/pages/progress-view.tsx:46-72`)
2. Calls `portalGetInvoiceUploadUrlFn` → gets presigned R2 upload URL (`portal/server.ts:148-171`)
3. PUTs file directly to R2
4. Calls `portalFinalizeUploadFn` → creates asset record with `ownerType='invoice'`, `usage='payment_proof'` (`portal/server.ts:87-113`)
5. Calls `submitPaymentProofFn` → redundant second insert (same data), which will fail on duplicate primary key — **this looks like a bug** (see Gaps section)

### PDF download
- Route `/api/documents/invoices/token/$token` (`src/routes/api/documents/invoices/token/$token.ts`) looks up the order by token, finds the first invoice for that order, and returns a generated PDF. **Only returns the first invoice** — if an order has multiple invoices, customers cannot download specific ones.

## 3. Permissions Controlling Invoice Access

- **Org-side**: `canManageInvoices(role)` in `src/features/permissions/model.ts:19-21` — only `owner` and `admin` roles can manage invoices. `member` cannot.
- **Portal**: No permission checks. Access is purely token-based — anyone with the order token can see all invoices for that order.
- The portal has no concept of roles; the token acts as the sole authorization gate.

## 5. How the Portal and Invoice Feature Communicate

### Shared infrastructure
- **Database**: Both use the same `invoices` and `paymentMethods` tables from `#/db/schema`.
- **Query keys**: Separate namespaces — `queryKeys.invoices.*` for org-side, `queryKeys.portal.*` for portal. No overlap.
- **Assets**: Payment proofs are stored as `assets` with `ownerType='invoice'`, `usage='payment_proof'`. Both sides could theoretically access them, but only the portal uploads them.

### Data flow
```
Org creates invoice → invoices table
  ↓
Portal fetches order (getPortalOrder) → JOINs invoices + payment_methods + checks assets for payment_proof
  ↓
Customer sees invoices + uploads proof → assets table (usage='payment_proof')
  ↓
Org marks as paid → invoices.status = 'paid', paidAt, paidBy
```

### Key observation: The portal and invoice feature are **decoupled at the code level**.
- The portal has its own `PortalInvoice` type (a subset of the full `Invoice` type) with flattened payment method data.
- The portal does NOT import from `#/features/invoices/` at all. It duplicates the invoice query logic in `portal/model.ts`.
- The invoice feature has no knowledge of payment-proof assets — it never queries the `assets` table.

## 6. Gaps: Org-Side vs. Customer Portal

### Critical gaps

1. **Org cannot view payment proofs**
   - Customers upload proof images/PDFs, but the invoice detail page (`invoice-detail-page.tsx`) has no section for viewing them.
   - The `getInvoice` function in `invoices/model.ts` does not query assets at all.
   - Admins have no way to verify that a customer actually sent payment.

2. **No "confirm payment" flow on org side**
   - The `confirmPayment` i18n key exists but no component uses it.
   - Admins can only "mark as paid" blindly — no UI to review the uploaded proof first.

3. **PDF download returns only the first invoice**
   - `/api/documents/invoices/token/$token` does `.limit(1)` on the invoice query. If an order has multiple invoices (e.g., deposit + final), the customer can only download the first one.

4. **Duplicate asset insert bug in payment proof submission**
   - In `progress-view.tsx:46-72`, `handleUpload` calls both `portalFinalizeUploadFn` AND `submitPaymentProofFn` with the same asset data. Both try to `insertAsset` with the same `assetId`. The second call should fail with a constraint violation. One of these calls is redundant.

5. **No invoice notification system**
   - Customers have no way to know when a new invoice is created unless they re-open the portal link.
   - No "new invoice" indicator exists in the portal UI.

6. **No payment history on portal**
   - Paid invoices are shown, but there's no `paidAt` date or `paidBy` info in `PortalInvoice`. The `markInvoicePaid` function records these fields, but they aren't exposed to the customer.

7. **Void invoices still visible**
   - `PaymentAlertBanner` filters out `paid` and `void` statuses, but `PaymentSection` still renders void invoices (just without the upload button). This could confuse customers.

8. **No "pendingPayment" or "failed" status support**
   - The status badge cast includes `pendingPayment` and `failed`, but the invoice table schema only has `unpaid | paid | void`. These statuses appear to be unused placeholders.

### Minor gaps

9. **No order-level payment summary** — the portal shows individual invoice amounts but no "total paid / total remaining" summary.
10. **No receipt download for paid invoices** — customers can download the invoice PDF but there's no receipt/proof-of-payment document after payment is confirmed.
11. **`paymentAllPaid` i18n key is unused** — should show a success banner when all invoices are paid.
